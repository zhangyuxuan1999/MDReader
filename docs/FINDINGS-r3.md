## Lens

Ran every pre-existing robustness script (s01–s20, all re-run from scratch against my own dev server on :5204) and wrote 18 new ones (s21–s38). The pre-existing suite passes in full — the only FAIL there, s09c check (d), is a wrong assertion in the test itself (it expects a collapsed 50k-entry TOC to render all 50 000 items; SPEC §5.7 says levels ≥ 3 are collapsed above 3 000 entries, and 16 668 top-level items is correct). The app is genuinely hard to break: 22 pathological documents, hostile environments (localStorage throwing, IndexedDB deleted / open() throwing / every readwrite transaction aborted, KaTeX module blocked), worker kills mid-burst, IME composition, 6 MB pastes, 100k-match replace-alls, 200-step undo/redo storms, mode+theme storms while typing, hidden-tab reloads, 500-level nesting, lone surrogates, RTL/emoji, 360 px viewports, 10 load/unload heap cycles and mountAll() over 100 002 blocks all produced correct output with zero console errors, zero page errors and no unintended restarts. Four real defects surfaced. The important one is a quadratic in the render worker: `edit()` (src/worker/core.ts:262) calls `resegmentWindow` once per change, and inside a single large block each call rescans the whole block, giving O(changes × lines-in-block). Measured at 9.51 ms per change in a 50 000-line block, so a plain search-panel Replace-all on the spec's own `pathological.md` case (one 50 000-line fence) stalls the worker past the 10 s silence watchdog and restarts the renderer with a 「渲染器已重启」 toast; the same operation split across 50 000 paragraph blocks costs 457 ms for 100 000 changes. Repeating it four times trips the client's restart cap, and because `gaveUp` in src/app/workerClient.ts:174 is a permanent latch rather than the sliding window the spec describes, the preview and the worker-side draft autosave stay dead for the whole session — even 90 s later — with only a page reload as recovery. The two low findings are a TypeError from `editor.gotoLine/scrollToLine` on NaN/undefined, and a 186 ms main-thread block when undoing a 100 000-change transaction. The dev server was killed and port 5204 verified free; no background processes remain.

### Findings (4)

- **[high] Worker `edit` handling is O(changes × lines-in-block): one Replace-all inside a large single block stalls the renderer past the 10 s watchdog and restarts it**
  - file: src/worker/core.ts:262
  - expected: A Replace-all (a spec'd feature, SPEC §7/§8, CM search panel) on a document class the spec explicitly targets (P6 "5k-line fence", P7 "unclosed ``` at line 1", `pathological.md` "one 50k-line fence") completes without tripping the worker-silence watchdog. SPEC §4.2/§10 budget the worker at 0.2–1 ms of splice+resegment per edit and the preview to update "within 1–2 frames".
  - actual: `edit()` applies the changes one at a time and calls `resegmentWindow` after EVERY change (src/worker/core.ts:262-266). Inside one giant block each `resegmentWindow` rescans the whole block, so the cost is O(changes × lines-in-block). Measured cost of a single transaction, time from `view.dispatch` to the worker's `structure` (s36):
  1 000-line block, 1 000 changes → 220 ms (0.22 ms/change)
  5 000-line block, 1 000 changes → 961 ms (0.96 ms/change)
  20 000-line block, 1 000 changes → 3 823 ms (3.82 ms/change)
  50 000-line block, 1 000 changes → 9 507 ms (9.51 ms/change)
  50 000-line block, 5 000 changes → >10 s → WORKER RESTARTED
  control, same 50 000 lines split into 50 000 paragraph blocks, 100 000 changes → 457 ms
In s37 the UI Replace-all produced `[workerClient] restarting render worker: no structure within 10 s` at +10 449 ms and the toast 「渲染器已重启」. In s34, repeating the operation restarted the renderer 4 times, which latches the permanent give-up (see the separate finding) — the preview and the worker-side draft autosave are then dead until a full page reload; `settle()` afterwards times out at 240 s. Plain typing hits the same wall without a restart but with a huge lag: a 1 200-char burst in a 50 000-line fence leaves the preview 12 776 ms behind the last keystroke (s38), vs the P5 target of 40 ms keystroke→mount.
  - repro: Start the dev server (`cd /Users/zyx/LocalDocuments/MDReader && npx vite --port 5204 --strictPort`), then:
1) End-user repro: `node bench/verify/s37_fence_replaceall_repro.mjs` — loads the spec's own pathological document (one 50 000-line ```js fence, SPEC §11 `pathological.md`), presses Mod-F, fills search="tok value" / replace="TOKEN value" and clicks the panel's Replace-all button (50 000 matches). No internal APIs are used.
2) Scaling matrix: `node bench/verify/s36_edit_matrix.mjs` (fresh page per row, prints a table).
3) Cascade into the permanent give-up: `node bench/verify/s34_restart_repro.mjs` (four restarts, then the renderer is dead for the rest of the session).
4) Same root cause via plain typing: `node bench/verify/s38_fence_typing_burst.mjs`.
  - fix: Do not resegment per change. In `edit()` (src/worker/core.ts:255-282) group the resolved changes into the maximal affected line window (or per containing block) and run `resegmentWindow` once per contiguous region after all the text splices of that region have been applied — `applyResolved` already returns the effect ranges, so they can be merged (reverse order already guarantees earlier changes keep their original coordinates). A cheap interim mitigation is to fall back to `segmentAll` when `changes.length × affectedBlockLines` exceeds a threshold, and to have the worker post an interim `structure` (or a heartbeat) while a long `edit` is in flight so `SILENCE_MS` cannot fire on legitimate work.
- **[medium] `gaveUp` in the worker client is a permanent latch, so the documented "≤ 3 restarts per minute" rate limit never reopens**
  - file: src/app/workerClient.ts:174
  - expected: SPEC §8/§9 specify a RATE limit — "max 3 restarts/min" — and `restartTimes` + `RESTART_WINDOW_MS` in the same function implement a sliding window. After the window expires, the next crash or silence should be allowed to restart the renderer again so the app self-heals.
  - actual: `restart()` begins with `if (disposed || gaveUp) return;` and sets `gaveUp = true` permanently once `restartTimes.length >= MAX_RESTARTS`; the pruned sliding window is never consulted again. Measured: after 4 crashes, `window.__workers.length` stays at 4 forever — 70 s later an edit plus 20 s of silence spawns no worker, `__wmsgs.structure` never advances past 1, and no typed text ever reaches the preview. Consequences observed: (a) the preview is frozen for the rest of the session; (b) the status bar keeps showing 「渲染中 100%」 and stale word/char counts; (c) worker-side draft autosave (SPEC §4.6) stops, so unsaved work has no IndexedDB backup and the user is not told; (d) the 「渲染器多次崩溃，已停止自动重启」 toast carries no action button (only the ×) — the only recovery is a manual page reload, which loses whatever the dead worker never drafted.
  - repro: `node bench/verify/s30_giveup_permanent.mjs` (dev server on :5204). It crashes the worker 4 times inside a minute, then types, waits 70 s (past `RESTART_WINDOW_MS = 60_000`), types again and waits another 20 s (past `SILENCE_MS`). Takes ~2 min. Also reproduced as the end state of `node bench/verify/s34_restart_repro.mjs`.
  - fix: Replace the permanent latch with the sliding window that is already computed: prune `restartTimes` on entry and only refuse a restart while `restartTimes.length >= MAX_RESTARTS` within the last `RESTART_WINDOW_MS` (clear `gaveUp` once the window drains), so a later crash can restart again. Additionally give the fatal toast an action (「重新加载」/「重试渲染器」) and put the status bar into an explicit error state instead of 「渲染中」, and surface that drafts are no longer being saved.
- **[low] `editor.gotoLine` / `editor.scrollToLine` throw a TypeError when the line argument is NaN or undefined**
  - file: src/editor/createEditor.ts:181
  - expected: The public `EditorApi` line-taking methods either clamp or ignore a non-finite argument, like the preview's equivalents do (`preview.blockAtLine`, `lineToScrollTop`, `scrollTopToLine`, `isLineVisible` all survive every value in the fuzz list, and `gotoLine(0 | -1 | 1e9 | null)` is clamped correctly).
  - actual: 4 throws, all TypeError "Cannot read properties of undefined (reading 'length')": `editor.gotoLine(NaN)`, `editor.scrollToLine(NaN)`, `editor.gotoLine(undefined)`, `editor.scrollToLine(undefined)`. `clampLine` (src/editor/createEditor.ts:181) is `Math.min(Math.max(1, Math.floor(line)), view.state.doc.lines)`, which returns NaN for a NaN/undefined input; `view.state.doc.line(NaN)` then yields undefined and `.length` / `.from` throws. Nothing in the current UI feeds NaN in (toc.ts and interactions.ts both guard), so this is an API-robustness nit rather than a user-visible bug — but `nav:gotoLine` is a public bus event any module may emit.
  - repro: `node bench/verify/s24_api_fuzz_mountall.mjs` — the "API fuzz" section calls every public line-taking editor/preview method with 0, -1, -1e9, 1e9, NaN, Infinity, 1.5, null and undefined.
  - fix: Make `clampLine` total: `const n = Math.floor(Number(line)); return Number.isFinite(n) ? Math.min(Math.max(1, n), view.state.doc.lines) : 1;` (or have `gotoLine`/`scrollToLine` return early on a non-finite argument).
- **[low] Undoing/applying a very large single transaction blocks the main thread for ~0.2 s (above the 100 ms input-latency budget)**
  - file: src/editor/changes.ts:5
  - expected: Input latency (keydown → next animation frame) under 100 ms for any single user gesture; SPEC P12 keeps the longest task under 50 ms.
  - actual: Undo of the 100 000-change transaction: keydown→frame latency 185.9 ms (wall 186 ms). Applying the same Replace-all: `view.dispatch` alone costs 252.1 ms on the main thread, and a 215 ms long task is recorded. The document result is correct in every case (all 100 000 replacements applied, undo restores the text byte-for-byte, structure tiles, preview matches a from-scratch render), so this is polish, not corruption.
  - repro: `node bench/verify/s33_search_extremes.mjs` section (B): a 50 000-line document, Replace-all over 100 000 matches from the search panel, then Mod-Z. Latency is measured by the keydown→next-frame probe in `bench/verify/_lib.mjs`. Dispatch cost also measured in `node bench/verify/s35_edit_scaling.mjs` (50 000 paragraph blocks, 100 000 changes).
  - fix: Flattening the ChangeSet (`flattenChanges`, src/editor/changes.ts:5) and building the `TextChange[]` for a 100 000-change transaction is a measurable part of this; consider transferring very large change sets to the worker in a packed typed-array form (like `packHtml`) instead of an array of objects with `ins.toString()` per change, and/or yielding the postMessage for change sets above a threshold so the frame after the gesture is not blocked.
